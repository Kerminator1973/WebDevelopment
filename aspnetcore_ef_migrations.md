# Работа с миграциями посредством Entity Framework

Добавить новую миграцию можно командой:

```shell
dotnet ef migrations add <ИмяМиграции>
```

Внести изменения в структуре базы данных можно командой:

```shell
dotnet ef database update
```

## Удаление миграций в базе данных и в коде

Проверка списка миграция в кодовой базе проекта осуществляется командой:

```shell
dotnet ef migrations list
```

Миграции, которые были созданы в проекте, но не опубликованы в конкретной базе данных (см. "appsettings.json") помечаются в выводе, как отложенные (Pending).

Удалить последнюю миграцию можно командой:

```shell
dotnet ef migrations remove
```

Повторять команду можно сколько угодно раз и инструмент будет удалять по одной миграции за раз. Однако, удаляются только миграции в статусе "Pending". Если нужно удалить миграции и из базы данных, и из кода, то сначала следует удалить их из базы данных, указав имя последней по времени, правильной миграции. Например:

```shell
dotnet ef database update NoDuende
```

Корректность удаления миграции из базы данных можно проверить запросом:

```shell
SELECT * FROM public."__EFMigrationsHistory"
ORDER BY "MigrationId" ASC LIMIT 100
```

После того, как миграции в коде будут отображаться в команде `dotnet ef migrations list` в состоянии Pending, можно начать удалять их из кода.

### Какие файлы формируются при создании миграции

Формируется файл с реализацией класса, который содержит команды применения (Up) и отката миграции (Down). Обычно такой файл имеет небольшой размер и легко читается.

Второй файл содержит в имени строку ".Designer." и реализует метод BuildTargetModel(), который строит модель базу данных с учётом применённой миграции с нуля. Файл Designer используется при генерации следующей миграции для того, чтобы идентифицировать изменения в модели и сформировать на основе этих изменений методы Up() и Down().

На практике, могут существовать ошибки при генерации кода миграций в Up() и Down(). Чаще всего это может быть связано с групповой работой над проектом и рассинхронизации действий программистов по изменению структуру базы данных. Если применение миграции к базе данных стало заканчиваться ошибкой, а реализация Up() и Down() содержит явные избыточности, то их можно удалить вручную. Если Designer-файл корректный, то никаких проблем при создании следующий миграций не будет.

## Переименовать таблицу с неудачным названием

Чтобы не потерять данные при переименовании таблицы, следует добавить следующий код в builder модели Entity Framework:

```csharp
public class MyDbContext : DbContext
{
    public DbSet<CastomPageTittleImageModel> CastomPageTittleImageModels { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<CastomPageTittleImageModel>()
            .ToTable("CustomPageMainImages");
    }
}
```

Затем следует создать новую миграцию и сгенерировать SQL-код, чтобы убедиться, что будет выполняться операция RenameTable, а не DropTable + CreateTable. Сгенерировать проверочный скрипт можно следующей командой:

```shell
dotnet ef migrations script
```

Если скрипт был сгенерирован корректно, то далее следует применить миграцию к базе данных.

Пример реальной команды для экспорта SQL-скрипта с поддержкой идемпотентности:

```shell
dotnet ef migrations script --idempotent --configuration Release --output ./Script.sql
```
