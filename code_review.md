# Автоматизация выполнения Code Review

Есть разные категории задач, для автоматизации **code review**:

- используя IDE-bases инструментальные средства. Инструменты предоставляют real-time feedback: синтаксическая подсветка, предложения по улучшению кода
- используя средства на базе технологии Git. Инструменты встроены в GitHub, GitLab, BitBucket, и т.д. Срабатывают при выполнении commit-а в репозитарий
- специализированные сайты и web-приложения. Используют разные инструменты: linter-ы (например, ESLint, Pylint), системы статического анализа кода (например, SonarQube) и AI-powered системы анализа кода (например: Codacy, CodeRabbit и DeepCode AI/Snyk)

## OWASP

Open Web Application Security Project — это открытый проект по безопасности веб‑приложений, который поддерживается некоммерческой организацией OWASP Foundation. Его цель — сделать приложения безопаснее за счёт открытых знаний: рекомендаций, стандартов, инструментов и обучающих материалов. Всё это бесплатно и доступно всем.

## Что это за проект

Это глобальное сообщество разработчиков, специалистов по информационной безопасности и исследователей. Его цель — сделать приложения безопаснее за счёт открытых знаний: рекомендаций, стандартов, инструментов и обучающих материалов. Всё это бесплатно и доступно всем.

### Ключевые продукты и проекты OWASP

- **OWASP Top 10** — список из десяти самых критичных рисков безопасности для веб‑приложений. Его обновляют примерно раз в 3–4 года, и на него ориентируются многие стандарты и практики. Например, в нём есть такие угрозы, как инъекции, нарушения контроля доступа, небезопасная конфигурация и др
- **OWASP ASVS** (Application Security Verification Standard) — стандарт для проверки уровня защищённости приложений. Его используют, чтобы понять, насколько приложение устойчиво к атакам
- **Руководства OWASP**: по разработке, тестированию, анализу кода. В них дают практические советы и примеры, как избегать уязвимостей на разных этапах создания ПО
- **Инструменты**: например, OWASP ZAP (Zed Attack Proxy) — прокси‑анализатор для поиска уязвимостей, удобный и для новичков, и для специалистов
- **Учебные проекты**: например, WebGoat — специально уязвимое приложение для тренировки навыков безопасной разработки и тестирования

**OWASP Dependency-Check** — бесплатный инструмент с открытым исходным кодом от OWASP для поиска уязвимостей в сторонних компонентах (библиотеках, зависимостях) вашего проекта. Его относят к классу SCA‑инструментов (Software Composition Analysis).

- Находит зависимости в проекте (читает pom.xml, build.gradle, package.json, requirements.txt и т. п.)
- Сопоставляет версии библиотек с базами известных уязвимостей — в первую очередь с NVD (National Vulnerability Database), а также с некоторыми дополнительными источниками
- Привязывает к зависимостям CVE: для каждой уязвимой библиотеки показывает список CVE, их CVSS‑оценки и описание
- Генерирует отчёт (HTML, JSON, XML, CSV, JUnit и др.) с перечнем проблем и рекомендациями

Для SonarQube существует плагин **dependency-check-sonar-plugin**, который не проводит собственный анализ кода или зависимостей, а встраивает готовый отчёт от Dependency-Check в консоль статистики и метрик в интерфейсе SonarQube: в списке проблем (issues), с метриками и возможностью отслеживать их статус.

## cve.org (ранее - cve.mitre.org)

Common Vulnerabilities and Exposures — стандартный словарь идентификаторов для публично известных уязвимостей в программном обеспечении и оборудовании. Проще говоря, это "единый язык" для обозначения дыр в безопасности: когда кто‑то находит уязвимость, ей присваивают уникальный CVE‑номер — и дальше все инструменты и базы говорят об одной и той же проблеме.

При этом CVE не даёт оценку опасности — для этого используют другие системы, например CVSS (Common Vulnerability Scoring System). Данные CVE часто берут в работу сторонние базы, такие как NVD (National Vulnerability Database), где уже добавляют оценки CVSS, списки затронутых версий и рекомендации.

Зачем это нужно при разработке:

- Управление зависимостями. Если вы используете библиотеки (например, драйвер БД, ORM, веб‑фреймворк), по CVE можно быстро проверить, есть ли в них критические уязвимости, влияющие на безопасность данных
- Патчинг и обновления. По CVE легко сопоставить уязвимость с нужным патчем от вендора
- Аудит и соответствие стандартам. В отчётах по безопасности и при проверках (например, PCI DSS, ISO 27001) принято ссылаться именно на CVE
- Автоматизация. CI/CD‑пайплайны могут автоматически проверять зависимости на наличие CVE с высоким CVSS и блокировать деплой, пока уязвимость не закрыта

OWASP даёт рекомендации и практики (например, как защищаться от инъекций), а CVE — это каталог реальных уязвимостей, где видно, как эти проблемы проявляются в реальных продуктах. Вместе они дают полную картину: OWASP учит, как не допустить уязвимость, а CVE помогает понять, какие проблемы уже нашли в используемых технологиях.
